## 1. 주제

### 1.1 프로젝트명

**본때 C팀 게임(SetStop) — 학교 축제 부스용 목표 시간 맞추기 웹 게임**

### 1.2 기획 배경과 목적

축제 방문자가 별도의 설명을 오래 듣지 않아도 바로 참여할 수 있는 짧고 직관적인 체험형 게임을 제작한다. 참가자는 10.00초를 목표로 타이머를 멈추며, 라운드가 진행될수록 누적되는 디메리트를 극복해야 한다. 단순한 시간 맞추기에 무작위 선택과 시각적 방해 요소를 더해 참가자와 관람객 모두가 결과를 함께 즐길 수 있도록 한다.

### 1.3 핵심 진행 방식

1. 참가자가 닉네임을 입력하고 게임을 시작한다.
2. 총 4개 라운드에서 목표 시간 10.00초에 맞춰 타이머를 멈춘다.
3. 1~3라운드는 각각 절대 오차 1.000초, 0.500초, 0.300초 이내여야 통과한다.
4. 각 통과 후 하 → 중 → 상 난이도 순서로 무작위 디메리트 2개 중 1개를 선택한다.
5. 4라운드는 탈락 없이 절대 오차로 최종 점수를 계산한다.
6. 점수는 자동 저장되며 별도 랭킹 화면에서 실시간에 가깝게 확인한다.
7. 등록 직후 현재 5위 이내인 참가자는 선택적으로 상품 연락처를 남길 수 있다.

### 1.4 운영 형태

- 게임 화면: 운영 노트북에서 `/game` 경로 사용
- 랭킹 화면: 부스 옆 태블릿에서 `/ranking` 경로 사용
- 서버: 정적 프론트엔드 빌드와 Node.js API를 함께 실행
- 기록 저장: 학교 서버의 `data/scores.json` 파일에 저장

## 2. 요구사항 명세

### 2.1 기능 요구사항

| ID | 요구사항 | 구현·판정 기준 | 상태 |
|---|---|---|---|
| FR-01 | 참가자 식별 | 1~12자의 닉네임을 입력해야 게임 시작 가능 | 구현 |
| FR-02 | 정밀 타이머 | 목표 10.00초, `performance.now()` 기반으로 시간을 측정 | 구현 |
| FR-03 | 라운드 통과 판정 | R1 ±1.000초, R2 ±0.500초, R3 ±0.300초 이내 통과. 제한과 같은 값도 통과 | 구현 |
| FR-04 | 최종 라운드 | R4는 탈락 없이 완료되며 절대 오차를 랭킹에 사용 | 구현 |
| FR-05 | 디메리트 선택 | R1·R2·R3 종료 후 하·중·상 난이도 후보를 각각 2개 무작위 제시하고 1개 선택 | 구현 |
| FR-06 | 디메리트 누적·충돌 방지 | 선택한 디메리트는 다음 라운드부터 누적 적용하며, 중복·충돌 후보는 제외 | 구현 |
| FR-07 | 화면 방해 효과 | 팝업·구름 자막은 타이머보다 위에 표시하고, 화면 반전은 HUD와 배경을 포함한 게임 화면 전체에 적용 | 구현 |
| FR-08 | 점수 계산 | `10000 - R4 절대 오차(ms)`, 최저 0점. 점수가 높을수록 상위 | 구현 |
| FR-09 | 자동 랭킹 등록 | 최종 결과 화면 진입 시 등록 버튼 없이 서버에 자동 저장 | 구현 |
| FR-10 | 랭킹 표시 | 점수 내림차순, 동점 시 R4 실제 오차와 등록 시각 순으로 정렬. 랭킹 화면은 3초마다 갱신 | 구현 |
| FR-11 | TOP 5 연락처 | 등록 직후 현재 5위 이내이면 등수와 전화번호 선택 입력 팝업 표시. 제출 시 서버가 최신 순위를 재확인 | 구현 |
| FR-12 | 연락처 선택권 | `등록 안 하기`를 제공하며 전화번호 미입력도 게임·랭킹 등록에 영향 없음 | 구현 |
| FR-13 | 경로 분리 | `/game`, `/ranking`, `/api`를 한 서버에서 제공 | 구현 |
| FR-14 | 개발 테스트 | 개발 환경에서 라운드 이동·디메리트 강제 적용 패널 제공 | 구현 |

### 2.2 비기능 요구사항

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| NFR-01 | 가독성·화면 활용 | 게임 화면은 고정 카드 테두리 없이 전체 화면을 사용하고, 기본 배율은 약 75% 수준으로 표시 |
| NFR-02 | 반응형 UI | 운영 노트북과 태블릿 해상도에서 주요 텍스트·버튼·타이머 위치가 깨지지 않아야 함 |
| NFR-03 | 데이터 지속성 | 서버·브라우저 재시작 후에도 `scores.json` 파일이 유지되면 랭킹이 보존되어야 함 |
| NFR-04 | 저장 안정성 | 임시 파일 작성 후 교체 방식으로 저장하고, 행사 운영 중에는 서버 프로세스를 1개만 사용 |
| NFR-05 | 개인정보 비공개 | 전화번호와 연락처 등록 토큰은 공개 랭킹 API 응답에 포함하지 않음 |
| NFR-06 | 운영 복구성 | 행사 전 초기화·운영 중 백업·오류 시 서버 재시작 절차를 준비 |
| NFR-07 | 브라우저 식별 | 브라우저 탭과 앱 메타데이터에 `본때 C팀 게임`을 표시 |

### 2.3 데이터 및 운영 요구사항

- 공개 랭킹 데이터: 닉네임, 점수, 최종 오차, 선택 디메리트, 등록 시각, 순위
- 비공개 데이터: 전화번호, 연락처 등록 토큰, 연락처 등록 시각
- 전화번호는 상품 안내 목적에만 사용하고, 상품 지급 종료 후 학교 지침에 따라 삭제한다.
- 상품 대상은 행사 종료 시점의 최종 순위로 확정한다. 현재 TOP 5여도 이후 기록에 따라 6위 밖으로 밀릴 수 있음을 참가자에게 안내한다.
- 동점으로 같은 순위가 여러 명 발생할 때의 상품 지급 기준은 행사 전 담당 교사와 협의해 확정한다.

## 3. 개발 계획

### 3.1 단계별 계획

| 단계 | 주요 작업 | 산출물·완료 기준 | 진행 상태 |
|---|---|---|---|
| 1. 기획·규칙 정의 | 게임 목표, 4라운드 구조, 통과 제한, 점수 방식 확정 | 기획서·게임 규칙 | 완료 |
| 2. 기본 게임 구현 | 닉네임, 타이머, 라운드 흐름, 결과 화면 구현 | 단독 플레이 가능한 프론트엔드 | 완료 |
| 3. 디메리트 구현 | DMR-001~010 모듈과 난이도·충돌 규칙 구현 | 무작위 2개 제시와 누적 적용 | 완료 |
| 4. 랭킹·서버 구현 | JSON 저장 API, 자동 등록, 랭킹 전용 경로 구현 | `/api`, `/ranking`, 데이터 파일 | 완료 |
| 5. UI·UX 개선 | 전체 화면 활용, 텍스트 가독성, 오버레이·반전·팝업 오류 개선 | 노트북·태블릿용 화면 | 진행 중 |
| 6. 통합 테스트 | 경계값, 중복 등록, 네트워크·서버 재시작, TOP 5 변동 검증 | 테스트 결과표·수정 내역 | 예정 |
| 7. 학교 서버 배포 | Node.js 실행 환경, 쓰기 권한, URL·방화벽 확인 | 실제 `/game`, `/ranking` 접속 | 예정 |
| 8. 축제 운영 준비 | 기기 배치, 점수 초기화, 백업·상품·개인정보 삭제 절차 확정 | 운영 체크리스트 | 예정 |

### 3.2 우선 테스트 항목

1. R1·R2·R3 제한값과 정확히 같은 오차가 통과하는지 확인한다.
2. 제한을 초과한 참가자가 다음 라운드·디메리트 선택으로 이동하지 않는지 확인한다.
3. 각 선택 차수에서 해당 난이도의 디메리트 2개가 무작위로 나오며 중복·충돌이 없는지 확인한다.
4. 화면 반전이 타이머뿐 아니라 라운드·디메리트 HUD와 배경 전체에 적용되는지 확인한다.
5. 팝업과 구름 자막이 타이머 위에 표시되고 팝업을 한 번의 클릭으로 닫을 수 있는지 확인한다.
6. 최종 화면에서 점수가 한 번만 자동 등록되고 새 기록이 랭킹 화면에 반영되는지 확인한다.
7. TOP 5 연락처 제출 직전에 순위가 밀린 경우 저장이 거절되고 안내가 표시되는지 확인한다.
8. 공개 랭킹 응답에 전화번호와 연락처 토큰이 노출되지 않는지 확인한다.

### 3.3 예상 위험과 대응

- 학교 서버에 Node.js 실행 권한이나 데이터 폴더 쓰기 권한이 없으면 점수 저장이 불가능하므로 사전 확인한다.
- 행사 중 네트워크가 끊기면 게임 화면과 랭킹 화면이 통신하지 못할 수 있으므로 같은 내부망 연결과 서버 상태 확인 방법을 준비한다.
- `scores.json` 손상·유실에 대비해 운영 중 주기적으로 별도 파일로 복사한다.
- 상품 기준과 동점 처리 방식, 전화번호 보관 종료일은 행사 전에 담당 교사와 확정한다.
